Three decisions visible on this screen

When is derived, never typed. The grid has already said when everything is. A second date field is a second source of truth, and it disagrees the first time somebody moves one slot.

The role name carries a warning. The activity flows shift → reconcile screen → hour entry → the letter, and it sits inside the reference digest. A role called "Trash Duty" is a line a judge reads.

Add-a-role and add-a-time are plain buttons. They can be server round-trips that re-render with a blank row, exactly as the quick-add screen already renders eight blank ones. There is no build step, so JavaScript enhances and never carries.

"What to know" sits on the role, not on the time

It is the existing _gwcvt_shift_notes — already on every shift, already labelled "What to know", and already reaching four places: the public list, the calendar file's description, the confirmation and the reminder. Nothing new is stored; the grid types it once per role and copies it to every shift that role creates, exactly as it does the role's name.

Because near enough every note anybody writes on a grid — hot work and closed shoes, some lifting, ring the bell at the north gate — is a fact about the work rather than about a particular hour. The consequence is that it shows on every time in that role, which is why both set-up times carry the lifting warning overleaf.

For a genuine one-off, the grid links each row to the single-shift editor that already exists — an event slot is a shift. That avoids a second notes box in the grid, and with it the question of whether a slot's note replaces the role's or is added to it.

03 / COORDINATOR

Removing a slot that has people on it

The rule that a shift with a roster is cancelled and never deleted does not lapse because the removal came from a grid instead of a button. An empty slot just goes. An occupied one asks — and it says which of the two is about to happen before it happens. Press Remove on either row.

Adding by hand already exists — it needs one field

gwcvt_handle_roster_add() takes a volunteer ID and calls gwcvt_add_signup() with source => 'staff'. It refuses an ID of 0 on purpose: a staff member typing a name and an address would be manufacturing an untriaged claim, which is the public form's job. The coordinator's job is to say who this is.

Events add the slot picker, and put the volunteer first — somebody doing this is on the phone to a person they already know, hunting for a time that suits. The fill count sits in each option so they can steer the call.

Two things this screen deliberately does not do

It does not refuse the double-booking. Capacity here is advisory and so is this: somebody working off a court order should not be bounced by a rule, and a coordinator who can see it can have a conversation. Tomas Iverson finishing set-up at 09:00 and greeting from 09:00 is not flagged — touching is not overlapping.

It does not log hours for the event. Each time is reconciled on its own, through the screen that already exists. An event never produces hours; only a shift does, and only after it has ended.

The event page

Radios become checkboxes and that is the whole structural change — still one form, still one nonce, still nothing that needs JavaScript. The full slot stays tickable, because full means the waiting list rather than no. The clash warning stops at the edge of the submission

Both slots are in the POST, so the check reads only what the sender just ticked and looks nothing up. That is what makes it safe — and it is also exactly why the other half cannot exist.

Asking whether the address just typed already holds an overlapping slot means querying earlier signups by email and then changing the page by the answer. That is the neighbour attack again: type somebody's address, tick Kitchen 08:00–14:00, and "that clashes with something you are already down for" reports that they hold something across those hours. gwcvt_find_signup() is licensed for its email lookup by one clause — "its answer changes nothing the visitor can see" — and a cross-submission warning spends that clause.

So a clash with an earlier submission is a coordinator-side flag on the roster, which is where screen 04 shows it.

Warned, not blocked — and why this is not the capacity argument

Being over the maximum is the organisation's constraint colliding with somebody who wants to come. An overlap is a physical impossibility and nearly always a misclick, and it fails towards the organisation: the slot reads as filled, the coordinator stops recruiting, nobody turns up. A phantom-filled slot is worse than an empty one.

It is still a warning rather than a refusal, because ducking out of the kitchen at noon to greet is a real thing people do. The form comes back with every tick intact, names the two, and asks once.

Counts, never names — and no setting changes it

This is the hardest divergence from the products this resembles, which publish their rosters by design. On a site running a court-ordered service programme, who is coming on Saturday is a list of people working one off. A place count says nothing about anybody; a first name says everything about one.

It is also why "2 places left" on a cached page is harmless. The page is a hint; gwcvt_settle_signups() is the authority, and it puts the overflow on a waiting list rather than turning anybody away.

06 / VOLUNTEER

What they are told

The most dangerous screen in the feature, and it is the one with the least on it. A multi-slot form begs for "you are signed up for 3 shifts" — and a count of what the database did answers a question the sender was never entitled to ask.

example.org/volunteer/fall-festival — after POST

Thank you — you are signed up. We have sent the details to your email address, along with a link you can use if you need to cancel.

Fall Festival

Saturday 12 October 2026 · Riverside Park, north gate

…the list follows, refreshed.

The attack this is guarding against

gwcvt_add_signup() is idempotent: signing up twice for the same slot refreshes the first rather than making a second. And the form never checks whether the address belongs to anybody.

So a stranger types your neighbour's email and ticks three boxes. Three new signups, or two new and one refresh, or three refreshes — if the response tells those apart, they have learned which of those slots your neighbour was already on, without ever being told a name. On a site running court-ordered service, that is a fact about a person they did not publish.

The leak is therefore a count of what the write did. A count of what was ticked reports only what the sender already knew, and a honeypot hit or a rate-limited attempt can produce that one too — so it does not break the byte-identical rule.

Why no number at all, even so

Not because a request-derived count is unsafe, but because the invariant is only cheap to hold in its blunt form. "This response contains no digits" is one assertion, the shape SelfLogTest already uses. "This response may contain a digit, but only one derived from the request and never from what the write returned" holds until the first person who thinks it would be friendlier to mention you were already down for the kitchen — and that arrives looking like a copy edit.

So: three slots, one slot, a honeypot hit and a rate-limited attempt all return the string already in the plugin, unchanged. Any slot no longer open returns the existing unavailable, with no count and no list of which. The detail goes in the email, which only that address receives.

07 / VOLUNTEER

The confirmation

One email per submission, not one per slot — four emails for four ticks is how an organisation teaches its volunteers to filter it. Each slot carries its own cancel link and its own calendar link, and that is what lets a token stay scoped to one slot while still answering "I can only drop the Sunday".

Why the queue groups, and why reminders do not

Confirmations already defer to shutdown; grouping them by claimed address and event is a change to the queue and nothing else. Reminders stay one per slot. Grouping them would break the one-to-one between a send and the _gwcvt_signup_reminded_at flag, and that flag is the whole reason a missed cron run sends late rather than never or twice.

The reminder, 48 hours out

Today's reminder says "you are down to volunteer on Saturday". Exact for one shift; for somebody holding three places it is ambiguous in the worst way, because the decline link drops one signup and the message never says which. So an event reminder lists what they hold, in the order the day happens, each declining on its own.

There is no "confirm you are still coming", and there will not be

Every product this resembles has that button. The asymmetry that rules it out: an unclicked cancel link means nothing; an unclicked confirm link looks like an answer. And then the answer has to be interpreted — a place dropped because somebody did not read an email, or a sorted list of people who do not reply, kept about a population working off court orders.

Prefetching makes it structurally worse rather than merely awkward. Cancelling is a POST behind a page because mail scanners follow links; a confirm link that survives that contact confirms everybody, and nothing tells the real ones apart. A feature whose commonest outcome is a wrong signal is worse than not having it, because the coordinator starts discounting the true signups too.

What keeps the hourly pass idempotent once it groups

Not one flag per email — that framing is what made this look impossible earlier. The invariant is: a slot's flag is set if and only if that slot was named in a message that was sent. Mark every slot you are about to mention, before sending, then send once.

Which settles multi-day events: mention only slots inside the window, mark exactly those. The Sunday slots keep their own flags and get their own message. Naming a slot without marking it sends it twice; marking one without naming it means it is never reminded about — and that failure is silent, so it is the one that needs the test.

09 / VOLUNTEER

Dropping one slot

The link from the email lands on a page with a button, never a bare GET. Mail clients prefetch links and security appliances follow them to see where they go — a GET that withdrew a place would eventually be withdrawn by a spam filter, and the volunteer would find out by not being expected.

One token means one slot, on purpose

It is tempting to have this panel list everything this address signed up for. That would be a lookup keyed on an email address — the shape the self-log form refuses to have, and a forwarded confirmation would then disclose the lot. The email already carries a link per slot, so the need is answered without the blast radius. The sentence above is doing that work: it tells somebody the other places are untouched, so they do not go hunting.

Open questions these screens raise

Should the flat "Coming up" view interleave event slots, or only summarise the event?

Drawn here as a summary row. Interleaving five festival slots among next Saturday's ordinary shifts buries them; omitting them entirely is a list that lies by omission. A single row that expands is the middle, and it is untested.

Does the volunteer need to see which roles they already hold when they come back to the page?

Currently no — the grid is identical for everybody, which is what keeps it free of any lookup keyed on identity. The cost is that somebody who signs up twice sees no acknowledgement on the page. gwcvt_add_signup() is already idempotent so nothing breaks; it is only unsatisfying.

Is "Need" and "Most" the right pair of words?

They are _gwcvt_shift_min and _gwcvt_shift_max, and the schedule screen currently never asks a coordinator to hold both in mind at once. Across a grid of eight rows it might want to be one number with an "or as many as turn up" option.

Should a role be able to span days?

The date sits on each row, so the Winter Coat Drive's two days already work. Whether the editor should group by day before role — or offer a "copy this role to Sunday" — is a real question for any event longer than one day.
